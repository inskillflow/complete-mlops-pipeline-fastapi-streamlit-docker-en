# Mini Lab — Testing Docker Agent with Docker Compose and MLflow

## Objective

The goal of this mini lab is to test Docker Agent, also known as Gordon, inside Docker Desktop.

The objective is not only to run Docker commands, but also to observe how an AI agent can help understand a Docker Compose architecture, detect possible configuration problems, suggest commands, and explain why a service behaves in a certain way.

This lab uses a Docker Compose workflow with MLflow and a training container.

---

## 1. Start Docker Desktop

Before running any command, open Docker Desktop and wait until it is fully running.

This is not a command.

Docker must be active before using `docker`, `docker compose`, or Docker Agent.

---

## 2. Open the project folder

Open the project folder in VS Code or in a terminal.

Make sure you are inside the correct directory, where the file `docker-compose-option2.yml` exists.

Run:

```bash
pwd
````

On Windows PowerShell, you can also use:

```powershell
Get-Location
```

Expected result:

You should see the path of the current project folder.

---

## 3. Verify Docker installation

Run the following commands:

```bash
docker --version
docker compose version
docker ps
```

Expected result:

* `docker --version` should display the installed Docker version.
* `docker compose version` should display the Docker Compose version.
* `docker ps` should show the list of running containers.

If Docker is not running, return to Docker Desktop and wait until it is fully started.

---

## 4. Start the MLflow service

Run:

```bash
docker compose -f docker-compose-option2.yml up -d --build mlflow
```

Explanation:

This command starts only the `mlflow` service defined inside `docker-compose-option2.yml`.

The option `-f docker-compose-option2.yml` tells Docker Compose to use this specific Compose file.

The option `-d` runs the service in detached mode.

The option `--build` rebuilds the image if needed.

---

## 5. Check running containers

Run:

```bash
docker ps
```

Expected result:

You should see a running container for MLflow.

If no container appears, check the logs:

```bash
docker compose -f docker-compose-option2.yml logs mlflow
```

---

## 6. Open MLflow in the browser

Open:

```text
http://localhost:5000
```

Expected result:

The MLflow interface should appear in the browser.

At this point, the MLflow server may be running, but no experiment may appear yet.

This is normal if no training job has been executed successfully.

---

## 7. Run the training container

Run:

```bash
docker compose -f docker-compose-option2.yml run --rm trainer --alpha 0.1 --l1_ratio 0.1
```

Explanation:

This command runs the `trainer` service defined in the Compose file.

The option `--rm` removes the temporary container after execution.

The parameters `--alpha` and `--l1_ratio` are passed to the training script.

---

## 8. Run more training experiments

Run:

```bash
docker compose -f docker-compose-option2.yml run --rm trainer --alpha 0.5 --l1_ratio 0.5
```

Then run:

```bash
docker compose -f docker-compose-option2.yml run --rm trainer --alpha 0.9 --l1_ratio 0.1
```

Expected result:

Each command should execute a training run.

After that, refresh the MLflow page:

```text
http://localhost:5000
```

You should now observe experiments or runs inside the MLflow interface.

---

## 9. Ask Docker Agent to inspect the project

Open Docker Agent / Gordon in Docker Desktop and ask:

```text
Please inspect my docker-compose-option2.yml file and explain the role of each service.
```

Expected analysis:

Docker Agent should identify the main services, explain the purpose of MLflow, explain the purpose of the trainer container, and describe how the containers communicate.

---

## 10. Ask Docker Agent to explain the command

Ask:

```text
Please explain this command step by step:

docker compose -f docker-compose-option2.yml run --rm trainer --alpha 0.1 --l1_ratio 0.1
```

Expected analysis:

Docker Agent should explain:

* why `-f docker-compose-option2.yml` is required;
* what `run` does;
* why `--rm` is used;
* what the `trainer` service represents;
* how `--alpha` and `--l1_ratio` are passed to the training script.

---

## 11. Ask Docker Agent to debug MLflow visibility

Ask:

```text
The training command runs, but I do not see the experiment in MLflow. Please inspect the Docker Compose configuration and explain the possible reasons.
```

Expected analysis:

Docker Agent may check whether:

* the trainer is logging to the correct MLflow tracking URI;
* the MLflow service name is correctly used inside the Docker network;
* the tracking server is reachable from the trainer container;
* the ports are correctly exposed;
* the volume configuration allows MLflow data to persist;
* the correct Compose file is being used.

---

## 12. Ask Docker Agent for the correct command

Ask:

```text
Based on this docker-compose-option2.yml file, what is the correct Docker Compose command to run the trainer service?
```

Expected result:

Docker Agent should suggest a command similar to:

```bash
docker compose -f docker-compose-option2.yml run --rm trainer --alpha 0.1 --l1_ratio 0.1
```

---

## 13. Compare human understanding and AI assistance

Answer the following questions:

1. Did Docker Agent only explain the command, or did it understand the Docker Compose architecture?

2. Did Docker Agent correctly identify the relationship between MLflow and the trainer container?

3. Did Docker Agent suggest commands that match the Compose file?

4. Did Docker Agent help debug the problem faster than manual inspection?

5. What are the limits of Docker Agent in this situation?

---

## 14. Important observation

Docker Agent is useful, but it should not be used blindly.

Every command suggested by the agent must be read and understood before execution.

An AI agent can help inspect, explain, and debug, but the human operator remains responsible for approving commands and validating the result.

## Optional Test — Ask Docker Agent to Analyze MLflow Experiments

Docker Agent can be used to help inspect the MLflow environment.

However, it is important to understand the difference:

Docker Agent does not replace MLflow.

MLflow stores and displays the experiments.

Docker Agent helps inspect the Docker environment around MLflow.

It can help verify whether the MLflow container is running, whether the trainer container can reach MLflow, whether the tracking URI is correct, and whether the experiments are really being logged.

Ask Docker Agent:

```text
Please inspect my Docker Compose configuration and explain how the trainer service connects to the MLflow service.
````

Then ask:

```text
Please check whether the MLflow container is running correctly and whether port 5000 is exposed.
```

Then ask:

```text
Please inspect the logs of the MLflow container and tell me if there are any errors.
```

Then ask:

```text
Please explain why my training runs may not appear in the MLflow interface after running the trainer container.
```

Then ask:

```text
Can you suggest a command or a Python script to list the MLflow experiments and runs from the tracking server?
```

Expected idea:

Docker Agent may suggest checking:

* the MLflow tracking URI;
* the Docker service name used by the trainer;
* the exposed port `5000`;
* the MLflow logs;
* the trainer logs;
* the mounted volumes;
* whether the correct Compose file is being used;
* whether the trainer actually calls `mlflow.log_param`, `mlflow.log_metric`, or `mlflow.log_artifact`.

Important conclusion:

Docker Agent can help analyze the Docker side of MLflow.

MLflow remains the tool that stores and displays the experiments.

The best workflow is:

Docker Agent for debugging the environment.

MLflow UI for visualizing experiments.

Python MLflow API for querying runs programmatically.
